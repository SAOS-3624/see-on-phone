# 鱼眼：去掉输出上限 + 让它在对话里画示意图（方案）

2026-11-23 · 用户要求：**PDF 编目不做、无障碍不做**；解决"思考一长就截断"；让对话里能显示 SVG 示意图。

---

## 0. 先砍掉两项

| 项 | 处置 |
|---|---|
| PDF 编目（一次生成目录+要点、按需展开原文） | **不做**。已经上线的"页数估算 / 解析费 / 预算扣减"保留 —— 那三样是**成本透明**，不是新功能，删了反而更糟 |
| 无障碍点屏幕（`AccessibilityService`） | **不做**。代码不写、权限不申请 |

---

## 1. "思考一长就截断"——到底是谁截的

代码里同时存在**三个上限**，但只有一个会产生"被截断"这句话：

| # | 上限 | 位置 | 实际行为 | 是不是元凶 |
|---|---|---|---|---|
| ① | `max_tokens`（默认 2000，上限 8000） | `Config.maxTokens()` → `Brain.assemble()` | 输出到顶就停，`finish_reason=length` → 界面加"到长度上限了" | **是** |
| ② | 工具轮总时长 90 秒（Agent 300 秒） | `Asker.BUDGET_MS` | 只在**两轮之间**判，单次回答不会中途被杀；多轮工具才会撞 | 次要 |
| ③ | socket 读超时 60 秒 | `Brain.readTimeoutMs` | 流式有字节进来就一直续，基本不触发 | 否 |

关键事实（从自家日志能对上）：**思考 token 也算进 `max_tokens`**。
11-22 22:45 那轮 `reason_len=407`（思考）、正文 ~300 字，而 `lastOut=735` —— 说明思考是算在
`completion_tokens` 里的。所以：

> 开"高"思考 → 先花 1500~3000 token 想 → 2000 的额度见底 → **正文刚开头就被切**。

这就是"思考一长就截断"的机制，不是网络问题。

### 方案（已按这个实现，2.7.2）

> 用户补充：**"要像 DeepSeek 官方 / 电脑端那样，不论思考多长都不截断，因为我要保质量"**。
> 所以不是"调大一点"，而是**默认不设限**。

1. **默认改成「自动」（0）**：`max_tokens = 1M − 这次输入估算 − 16K 余量`，
   再夹到官方单次上限 **384K**。
   - 为什么不直接写 384000：`输入 + 输出` 不能超过 1M 窗口，带着 90 万历史再要 384K 会被 400；
     现算之后"能写多长"永远等于"窗口真的还剩多少"。
   - 为什么不能干脆不写这个键：不同端点默认值不一样（有的 4K），等于把上限交给对方。
2. **档位**：自动 / 8000 / 16000 / 32000 / 65536 / 131072。想省钱的人仍可手选固定值。
3. **兼容端点兜底**：自动值可能算到 384K，而某些端点只认 8K/32K → 回 400。
   `Asker` 识别 `max_tokens` 类 400 后**自动降到 16384 重试一次**，不把错误丢给用户。
4. **超时不再误杀**：socket 读超时 60 → **180 秒**（这是"多久没字节"，不是总时长）；
   `/ask` 同步接口 90 → 600 秒；`Asker` 两轮之间的总预算 90/300 → **300/900 秒**。
5. **截断文案分两种**：手设了小值 → 告诉你改回"自动"；真写满 384K → 说"回「继续」"。

实测（2.7.2，高思考，要求写四千字）：

```
brain stream ... max=384000
ask round=1 reason_len=7664 finish=stop took=64622ms
lastOut=8301
```

思考 7664 token、输出合计 8301 token、`finish=stop` —— 旧版 2000 的额度连思考都不够，
正文必然被切；现在完整收尾。

## 2. 为什么现在画不了图

现在的渲染链是：`Markdown.render()` → `SpannableStringBuilder` → `TextView.setText()`。
`Markdown` 只认**六种**标记（粗体/斜体/行内码/代码块/列表/标题），**代码块只上色不解析**。
所以模型就算写了 ```svg```，也只是变成一段绿色等宽文字 —— 不是它不会画，是**这边没人画**。

另外模型自己也有顾虑：它不确定这边能不能渲染，多半会退回 ASCII 示意图（`┌──┐`）。

## 3. 三种做法（选一个）

| 方案 | 做法 | 体积 | 保真度 | 风险 |
|---|---|---|---|---|
| **A. 迷你光栅器（已实现）** | 自己解析 SVG 子集，用 `Canvas` 画到 `Bitmap`，放进 `ImageView` | +8KB（APK 322KB） | 子集内 100% | 解析器要写得稳；不支持渐变/滤镜 |
| B. WebView | 每张图一个 `WebView` | +6KB 代码 | 100% | 每个 20~40MB 内存；气泡里嵌套滚动/长按全坏 |
| C. 结构化 DSL | 给模型 `draw` 工具传 JSON | +8KB | 只能画框和箭头 | 表达力最弱 |

**最终实现**：`Svg.java`（约 520 行，纯 `Canvas`）+ `Bubbles` 里把 ```svg 段抽出来当 `ImageView`。

⚠️ **`ImageSpan` 这条路走不通（真机验证）**：占位、行高、宽度都对，`Drawable.draw()`
就是不落到屏幕上（换成 `BitmapDrawable` 也一样）。所以改由 `Svg.extract()`
把围栏段摘出来单独渲染成 `ImageView` —— 缩放、圆角、长按一次到位。

### 实现里踩到的两个真 bug（都是"图是黑的/字叠在一起"）

1. **图形自己的属性没读**：只给 `<g>` 读了样式，`<rect fill="#eef3fa">` 的 `fill` 被忽略，
   于是每个框都按默认**黑色**填充 —— 整张图黑成一片，看起来就是"气泡里空了一块"。
2. **`<text>` 的 x/y 取晚了**：`text(p)` 会把解析器推到 `</text>`，之后再读 `x/y`
   全是 null，所有文字画在 `(0,0)` 叠成一坨。改成**先取坐标再读正文**。

### 支持子集

```
<svg viewBox>  <g transform="translate|scale">  <rect rx>  <circle>  <ellipse>
<line>  <polyline>  <polygon>  <path d="M L H V C Q Z">  <text>
属性：fill / stroke / stroke-width / opacity / fill-opacity / stroke-opacity /
      font-size / text-anchor / font-weight / style="…"
```

不支持就整块回退成代码块（返回 null），**绝不画半张**。

### 落地细节

1. **浅色底**：统一铺 `#FFFFFF` + 12px 留白 —— 模型默认写黑字，深色主题上才看得见。
2. **按屏宽渲染**：宽度 = 屏宽 × 0.8（≤900），`LruCache` 按（源码 hash + 宽度）缓存。
3. **一条最多 3 张**、单张源码 ≤ 20KB、高度上限 1800px。
4. **流式**：围栏没闭合时按代码块显示（不画半张）；收尾时一次性替换成图。
5. **提示词**：`SYSTEM` 里明确写"这边会真的渲染成图"，否则它会退回 ASCII。

实测（真机截屏 + 落盘比对）：4 个圆角框 + 箭头 + 中文标签，浅底、字清楚、宽度自适应。

## 3.5 用量面板（像 DSH 那样拆）

顶栏圆环点开，现在显示：

```
上下文：27,370 / 900,000（3%）
本轮输入 4,948
　· 缓存命中 128　· 未命中 4,820　· 命中率 3%
本轮输出 1,659 · 工具 0 次
本轮花费 $0.001719（缓存省下 $0.000019）
累计：输入 4,948（命中 128） · 输出 1,659
累计花费：$0.0194
```

要读的三个数：`usage.prompt_cache_hit_tokens`（兼容 `prompt_tokens_details.cached_tokens`）
→ 命中；`prompt_tokens − 命中` → 未命中；`completion_tokens` → 输出（**含思考**）。
累计三行（in/out/hit）落在 `Config` 里，重启不丢。

## 4. 工作量与顺序

| 顺序 | 事项 | 规模 | 说明 |
|---|---|---|---|
| P0 | 输出上限（max_tokens 档位 + 思考余量 + 看门狗 + 文案） | ~80 行，改 4 个文件 | 用户当前最痛，先上 |
| P1 | `Svg.java` 光栅器 | ~550 行新文件 | 与现有代码零耦合，能离线单测（纯 `Canvas`） |
| P1 | `Markdown` 识别 ```svg + `Bubbles` 缓存 | ~120 行 | 失败回退成代码块 |
| P2 | 提示词 + 设置页文案 | ~30 行 | 让模型愿意画 |

两批可以一起发（2.7.0）。

## 5. 风险与回滚

| 风险 | 处置 |
|---|---|
| 放开 `max_tokens` 后一次吐太长、把"通话页"线程占住 | 只影响用户主动要长文；`cancelTurn()` 仍能中断（已有 socket 断开 + interrupt）；硬顶 15 分钟 |
| 看门狗误杀（长 prefill 期间真的没字节） | 45 秒阈值 + 只在**已建立连接后**计时；出现误杀改回 90s 总时长只需一个常量 |
| SVG 解析崩 | 整个渲染包在 `try/catch`，失败回退代码块；单条消息限额 3 张 |
| 图太大撑爆内存 | 高度上限 1200px、单张最大 8KB 源码、`LruCache` 上限 12MB |
| 模型开始滥用 SVG（每条都画） | 提示词写"只在用户要图/解释结构时画"；一条最多 3 张 |

## 6. 验收

1. 开"高"思考问一个需要长答案的问题（"讲讲 XX 的来龙去脉，1500 字"）→ **不再出现截断提示**，
   日志里 `lastOut` 明显大于 2000。
2. 设 2000 档 → 仍然会在 2000 附近截断，提示里告诉你去哪调（回归验证档位真的生效）。
3. 让它"画一个三层架构示意图（SVG）"→ 气泡里出现**图片**（浅底、字清楚），不是代码块。
4. 故意让它写一段带 `<style>` 的 SVG → 回退成代码块，不崩、不吞。
5. 流式过程中观察 CPU：同一张图不重复光栅化（缓存命中）。
